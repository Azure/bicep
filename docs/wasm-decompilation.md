# WebAssembly decompilation results

The playground compiler client's `decompile(jsonContent: string)` method returns
the JSON-serialized result of `Bicep.Wasm.Interop.Decompile`. The input is an ARM
template string and the result has this shape:

```typescript
type DecompileResult = {
  bicepFile: string | null;
  error: string | null;
  entrypoint: string | null;
  files: Record<string, string> | null;
};
```

On success, `error` is null, `entrypoint` is `"main.bicep"`, and `files` includes
the entrypoint and every generated Bicep module. Its keys are relative paths
rooted alongside the entrypoint, using `/` separators rather than filesystem
paths or absolute URIs. Resolve module references relative to their containing
file.

For example, an ARM template containing an inline nested deployment can return
`main.bicep` and `nested_child.bicep`. The entrypoint contains a module reference
to `./nested_child.bicep`, and the corresponding `files` entry contains that
module's source. Further inline nested deployments are also included.

The existing `bicepFile` field remains the entrypoint's source:
`bicepFile === files[entrypoint]`. Consumers that only read `bicepFile` and `error`
continue to work. This does not add a multi-file editor to the playground.

On failure, `error` contains the failure message and `bicepFile`, `entrypoint`,
and `files` are all null.

This result exposes files already generated by the decompiler; it does not
change nested deployment conversion or outer-scope parameter rewriting. It
does not resolve external linked templates or add a multi-file compilation
API. Linked templates may still produce unresolved module references.
